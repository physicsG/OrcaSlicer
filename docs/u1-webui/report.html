Reverse engineering · Snapmaker Orca

Inside the U1’s embedded web UI

The Device tab and the print-processing popup are not C++. They are the same compiled Flutter application, talking to Orca through a single JSON bridge — and that bridge, its command set, and the printer protocol behind it are all recoverable from the bundle that already ships in this repo.

Method

Three sources that check each other

The bundle is minified, but dart2js mangles identifiers, not string literals. Enum value names, class names, wire field names and the whole command table survive verbatim. That gives one source. Orca’s own SSWCP.cpp and MoonRaker.cpp implement the other end of the same contract, giving a second.

The third is the most useful and the least obvious: the bundle is a web app, so it runs in an ordinary browser. Serving it against a simulated host turns static reading into something testable — you assert how the protocol works, implement that, and watch whether the real page agrees.

harness tree symlinks to the real bundle + an edited index.html | +- cloud-stub.js intercepts fetch/XHR to *.snapmaker.com +- wcp-bridge.js implements window.wx, records every request +- inject-state.js canned host responses, per command | harness_server.py serves at /web/flutter_web/ (the bundle’s base href) cdp.py + shoot.py drive headless Chrome over the DevTools Protocol | +-> screenshots + a JSON log of every bridge call the page made

The recorder pays for itself immediately: rather than guessing what the Device page asks for at boot, the page reports it. And because the page logs its own construction back to the host through sw_FileLog, its internal component graph (OrcaGateway, LavaDeviceViewModel, OrcaAuthBridge, OrcaControlViewModel) reads straight out of the capture.

Surface 01

The Device tab

Mounted at ?path=2. Three regions: a left rail with the device selector, a camera panel, and a control panel. The control grid is the part that matters — a temperature column, a four-toolhead selector, a jog-step selector, home, and the jog arrows.

Worth knowing

The login gate is reached by more paths than an actually signed-out user. In the harness the account handshake succeeded, and the gate still appeared — because the page then calls the Snapmaker cloud API (getUserAwsIoTConfig, getCloudDeviceList) and treats a failure there as _handleUserOffline.

So an unreachable cloud is indistinguishable, at this gate, from a signed-out account. That is worth remembering when triaging “it keeps asking me to log in” on a LAN-only setup.

Surface 02

The print-processing popup

A modal 714×750 dialog that opens between “Send to printer” and the job actually starting. Which of its two routes loads is decided by the post-upload action the user picked in the preceding native dialog.

// Plater.cpp
dialog->set_send_page(dlg.post_action() == PrintHostPostUploadAction::None);

// WebPreprintDialog::run()
auto real_url = m_send_page ? m_preSend_url    // path=5, upload only
                            : m_prePrint_url;  // path=4, upload and print

The two captures settle what the route names mean: preUpload really is upload-only, and preUploadAndPrint really does add the print setup. The three preference toggles map onto fields of the print_task_config object that the Device page also subscribes to.

The dialog closes itself over the bridge

There is no native OK button. The page ends the modal by calling two commands, and the split between them is deliberate — one records the outcome, the other closes.

sw_SetFilamentMappingComplete { status: "success" | "canceled" }
    -> dialog->set_finish(...)   // records, does NOT close

sw_FinishFilamentMapping
    -> SafeEndModal(is_finish() ? wxID_OK : wxID_CANCEL)

The host comments say why: the page, the window manager and the close handler can all race to end the same dialog, so SafeEndModal makes it idempotent behind an m_modal_ended flag.

Bridge

One channel each way

Snapmaker calls it WCP. Both directions carry JSON strings, and both surfaces share one command set — the Device tab and the popup forward script messages to the same SSWCP::handle_web_message.

// page -> host
window.wx.postMessage(JSON.stringify({
  header:  { seqid: "1787477198605001" },
  payload: { cmd: "sw_GetConnectedMachine", params: {}, event_id: null }
}));

// host -> page
window.postMessage(JSON.stringify({
  header:  { seqid: "1787477198605001" },        // echoed verbatim
  payload: { code: 200, message: "success", data: {} }
}), '*');
Finding

The success code is 200, not 0. The status field defaults to an HTTP-like 200 in SSWCP.hpp, and the page compares against 200 literally. Replying 0 — the natural guess for “no error” — makes the page raise Exception: getUserLoginState failed: code=0, message=success, retry three times, and then declare the user logged out.

This was found by getting it wrong in the harness: 0 produced a login gate, 200 let the session proceed to ConnectionStatus.connectedOnline.

event_id decides lifetime. With one, the host registers an infinite-lived subscription; without one, the instance is collected on a timeout. Eleven commands are subscriptions, each with its own push-channel name. The page gives the host 3 seconds per request, and retries account calls three times.

The page owns the protocol

This is the structural fact that makes the whole surface recoverable. The bundle builds complete JSON-RPC envelopes — method names, parameter maps, subscription field filters — and hands them down. It even drives the MQTT session: sw_create_mqtt_client, sw_mqtt_connect, sw_mqtt_subscribe, sw_mqtt_publish. The C++ owns the socket; the compiled Flutter page decides what goes through it.

MQTT 5 over TLS on port 8883, QoS 1, namespaced by printer serial. The U1 runs Klipper behind a Moonraker-derived API, with Snapmaker extensions under camera.*, custom.* and printer.control.*.

Recovered

What fell out of the constant pool

dart2js lowers each Dart enum value to a constant-pool entry of the form B.x = new A.sym(index, "name"), and the conventional toString override leaks the type name as "TypeName." + this.b. Grouping by type symbol reconstructs every enum in declaration order, with real names.

That yields 274 enums and 1,370 values, 272 of them with their true Dart type name, rendered as readable source in reconstructed/enums.dart. The domain-carrying ones are exactly the ones you would want:

EnumValuesRole
WcpCmd93the bridge command set
DeviceStatusType26displayed status, every failure mode
DeviceStatus15what the machine is doing

DeviceConnectionError9why a connection failed
PrintState8job state
SendButtonState8the popup’s Send button

A second getter on WcpCmd maps each index to its wire name, which is what makes the command catalogue exact rather than inferred. Cross-referencing it against the C++ exposes real version skew between the shipped bundle and the host: 111 commands on both sides, 5 the page can emit that nothing answers, 13 the host implements that the page’s enum does not know about.

The clearest case: the enum declares both sw_UnSubscribeMachineState (index 7) and sw_StopMachineStateSubscription (index 10), but the host implements only the latter. A call on index 7 would go unanswered and fail on the 3-second timeout.

Error codes decode cleanly

The 72 shipped codes are 8 hex digits with real structure — four digits of subsystem, one of severity, three of fault index.

PrefixCountSubsystem
030023motion, homing, bed and nozzle temperature
05009print-job submission and cloud transport
0700–070336filament path — the same 9 faults, once per toolhead
0C004defect detection (first layer / spaghetti)

The four 0700–0703 banks are the strongest structural signal in the table: an identical nine-fault set repeated four times. That is what identifies the third byte as a toolhead index — and independently confirms the four toolheads visible in the Device tab screenshot.

The severity digit is meaningful in the UI: 4 is terminal, 8 renders with a retry or resume affordance, and C is advisory — the two 0C00C codes are the “possible defect” variants of the two confirmed 0C008 ones.

Fork leftovers, user-visible

Three 0500 codes still name Bambu Cloud (“Failed to connect to Bambu Cloud…”), and several 0700 texts refer to the AMS where the U1’s equivalent is the ACE. Eight codes ship with an empty string in every locale — xxxx8007 and xxxx8010 in each toolhead bank — so a printer reporting one would surface a blank message.

Corrections

Two things the earlier notes had wrong

The existing docs/u1-webui/ describes ?path=1 as a developer route menu. It is not — loading it renders the Home / Model Library page: a “Recommended for You” grid of community models fetched live from Snapmaker’s CDN, with Model Library / My Devices / Recent Files navigation.

A developer route menu does exist in the bundle, as a column of buttons calling Navigator.pushNamed(context, "/deviceControl") and friends. But it is a separate screen that links to these routes; the ?path= dispatcher never uses those strings, and returns AppModule values directly. The two mechanisms are independent.

The route numbers are crossed

For every module except two, the URL number equals the AppModule enum index. The print-popup routes are the exception:

URLModuleEnum index
?path=2deviceControl2
?path=3deviceControlOld3
?path=4preUploadAndPrint5
?path=5preUpload4
?path=6testPrintUploadTask6

It is harmless — nothing derives the URL from the index, and the C++ is consistent with the names — but you cannot assume path == AppModule.index. The extractor flags it rather than normalising it away.

Also still shipping in the release bundle: ?path=6 and ?path=7 are test-only harnesses, ?path=3 is a superseded Device page, and the bundle carries a hard-coded internal Snapmaker host at http://172.17.100.32:8100/api alongside pre-production cloud hostnames.

Limits

What is not proven here

This is the client side: the bundle in this repo and the Orca C++ it talks to. Printer-side behaviour — what firmware actually does with each call — is inferred from the client contract and from MoonRaker.cpp, not observed. Anything inferred is marked as such where it appears in the docs.

A fully connected Device page with live telemetry was not reached. The session additionally depends on the page’s own deviceList and deviceFilamentInfo caches, which the page writes and the host merely relays, so the control grid renders disabled in every capture. Everything up to ConnectionStatus.connectedOnline does work with the cloud stub in place; the remaining gap is state, not protocol.

The subsystem labels on the error prefixes are derived from the faults grouped under each, not from any manifest that names them. The 0700–0703 reading is strongly evidenced by the four identical banks; the others are ordinary inference.
