Two surfaces, one model

Two agents reverse engineered the same bundle on the same branch. Merging the results resolved one contradiction that would have broken every real response, separated two error tables that had been mistaken for one, and left a shared layer that both reconstructed surfaces now build on.

The one that mattered

One pass documented payload.code: 0 as success and built its client and its simulated host around that. The other found 200. They cannot both be right, and the difference is not cosmetic: a client that accepts only 0 rejects every real response from Orca.

// what the client did
if (code === 0 || code === undefined) resolve(payload.data);
else reject(new SswcpError(code, payload.message, cmd));

// what Orca actually sends
int m_status = 200;   // SSWCP.hpp:219, the default on every success path

Three independent confirmations settled it:

  1. The C++ default is m_status = 200, and every handler that succeeds without touching it replies 200.
  2. The shipped bundle compares payload.code against the literal 200 in eleven places, and against no other integer.
  3. Replying 0 from a simulated host makes the real page raise getUserLoginState failed: code=0, message=success, retry three times, and declare the user signed out.
Now guarded

The predicate is one definition (OK_CODE, isOk()) in the shared bridge client, the simulated host replies with it, and three conformance checks pin it. The checks were negative-controlled — setting OK_CODE = 0 turns the suite red.

The two that were not conflicts

The U1 ships two error tables. The live one is 442 codes in 16 hex digits, carried in the i18n table as error_<16 hex>_title / _desc pairs. The other is 72 codes in 8 hex digits in deviceError.json — a Bambu-era asset, which is why several of its strings still say “Bambu Cloud” and “AMS”. Each pass had found a different one. Both are now documented, with the legacy one explicitly marked as not the live fault table.

Structure

Each surface has its own folder

Two documentation roots became one, with a folder per surface and an explicit shared section. Nothing was dropped: where the two passes covered the same ground differently, both views were kept when they answered different questions — the command tables and the JSON-RPC surface each now have a generated reference and a hand-written narrative.

The hinge is print_task_config

This is the single most useful thing to know before modifying either surface. One Klipper object, read by one surface and written by the other:

print_task_config | reads | writes ┌────────────────────┴────────────────────┐ │ │ Device tab Print-processing popup labels each toolhead with edits the filament→toolhead the filament loaded in it mapping and the three toggles

The popup’s three Print Preferences toggles are literally fields of it — flow_calibrate, time_lapse_camera, auto_bed_leveling. So a change to how filament is modelled lands in both places, and the Device tab’s toolhead cards are the second one to remember.

Trap found while merging

The Device tab commits to a single dark look and overrides :root wholesale. It must therefore define every token the shared stylesheet styles against — not just the ones its own rules use — or shared components render its dark panels with the base stylesheet’s light-theme text. That is exactly what happened to the build badge on first run; device.css now carries explicit aliases.

Marker

The build badge

Both surfaces now render a badge in the bottom-right corner naming the surface and the build they report. It is the smallest change that is still unmissable: one fixed element, no layout shift, no interaction.

Both mount it identically, which is the point:

// device_page/js/app.js
mountBuildBadge(ui.$('#build-badge'), 'Device', bridge);

// print_processing/js/app.js
mountBuildBadge(ui.$('#build-badge'), 'Print processing', bridge);

To confirm it is reading the real file rather than a baked-in constant: change build_number in resources/web/flutter_web/version.json, reload with no host, and the badge follows.

Limits

What this still does not prove

Both reconstructions are verified against a simulator built from the same documentation. That proves internal consistency and that the client logic works; it does not prove a real U1 agrees. Validating against hardware remains the outstanding step, and it is the one that would most raise confidence.

The code: 200 finding is the exception — it is confirmed against the shipped bundle’s own comparisons and Orca’s C++, not just against a simulator.

Surface-specific gaps: the popup’s printer picker is a stub, its upload progress is simulated locally, and sw_GetPrintZip is called but its content unused. The Device tab covers live machine control only — discovery, pairing, cloud login, the file browser, camera and timelapse are documented but not built.
