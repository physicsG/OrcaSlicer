Mockup — Printer settings › Multimaterial, proposed multiACE topology UX. The group is the addition; everything else is the page as it ships today. See docs/ace-mmu/12-topology-config-ux.md for the full options and trade-offs.

What changed and why. The previous version asked for two raw numbers per toolhead, and all three of its problems bit us in practice. (1) slots = 1 was a magic value: it reads as a quantity but actually means no ACE. It is now spelled “Stock feeder”. (2) The unit was 0-based while every other surface calls the first unit ACE 1. The UI that showed you the answer disagreed with the field that wanted it, which is exactly how a head wired to the first ACE got configured as 1. Labels are now 1-based everywhere, and they name the ACE unit — the hardware, which may be an ACE Pro, an ACE 2 Pro, and so on. multiACE is the layer that drives them, so it appears in the group header and nowhere else. (3) The unit field appeared on heads with no ACE, where it means nothing; the slot count now appears only when a head is actually ACE-fed.

Consolidating the config. The same topology currently lives in three places: multiACE’s own page on the printer (authoritative — ACE_SET_HEAD_ACE and friends persist it), the U1 + multiACE device page (a live mirror), and here (hand-typed, and therefore able to disagree). The printer already reports all of it via /multiace/api/state, so Sync from printer makes the machine the source of truth in one click, and Orca’s copy becomes a cache that keeps offline slicing working. The second group shows the case that matters: when the preset and the machine disagree, it is stated plainly with a one-click fix — instead of silently emitting ACE= pointing at the wrong unit. The end state (option D) moves authoring to the device page entirely, leaving this as a read-only summary.
