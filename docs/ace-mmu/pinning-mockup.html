Pinning a spool in place

A pin says this colour stays here — the optimiser plans around it instead of moving it. The planner already honours pins as hard constraints and the board already lets you set them. Two things are wrong with that today, and one of them makes the feature invisible.

Everything arrives pinned. C++ seeds the page with the computed plan expressed as pins — one per filament — so the board opens saying Auto plan honours 7 pin(s) with an orange pin on every spool. A badge that every spool carries distinguishes nothing, and a deliberate pin is indistinguishable from the optimiser's own choice.

And pins do not survive. Unlike an applied layout, which now rides in the 3MF with its plate, a pin is gone the moment the dialog closes.

TodayEvery spool wears a pin

The seeding exists for a good reason: it guarantees the board shows exactly the layout the gcode will use, rather than the page's own optimiser re-deriving an equal-cost but differently-arranged one. Removing it naively would let the board lie about where spools go — so the fix is to send the layout as a layout, and keep pins for pins.

ProposedOnly what you pin is pinned

Two spools pinned, five free. The header counts the real pins, the pinned spools are ringed as well as badged, and Clear pins now has something to clear. Auto re-optimises around the two, which is what a pin is for — here it costs 12 swaps over the free optimum, and the header says so.

ProposedPins come back with the plate

Reopened project: the two pins are restored, and one that no longer fits — its slot is gone because the ACE was reconfigured from four slots to two — is dropped and said out loud, exactly as a remembered layout is when the filament count changes.

A bug to fix alongside

pinTo() records the slot only when the head index is literally 3: state.slotPins[colour] = head===3 ? slot : -1. On a machine with two ACE-fed heads — which the two-unit work just made real — pinning into the other ACE head keeps the head but silently loses the slot. It should test whether the head is ACE-fed, not whether it happens to be the fourth one.

What I need from you

  1. Seeded ≠ pinned. Recommended: C++ sends its plan as the layout and sends only real pins as pins. The board still matches the gcode exactly; the pin badge starts meaning something.
  2. Do pins persist with the plate? Recommended: yes, by the same mechanism as the applied layout — a per-plate option in the 3MF. The alternative is that pins last only as long as the dialog, which is what happens now and is why nobody would use them.
  3. Pin to a head, or to an exact slot? The board supports both. Pinning to a head says "keep this colour on T4"; to a slot, "keep it in T4 · S2". Slot-exact is stricter and is what a physical spool actually occupies; head-only leaves the optimiser room to reshuffle within the ACE.
  4. A pin that no longer fits — drop it silently, or say so as drawn in the third panel?

What already exists

Planner: PlanPin in AceMmuPlan.hpp already takes a head, an ACE unit or an exact slot, and treats it as a hard constraint — the search optimises the free colours around it. No solver work is needed. Page: pin/unpin by click and by drag already work, and optimise(state.pins) already respects them. Persistence: the pattern is in place from the applied layout — a per-plate coInts option, written to plate metadata in the 3MF, re-priced on load. What is missing is the distinction between a seeded position and a pin, the persistence itself, and the head===3 fix.
