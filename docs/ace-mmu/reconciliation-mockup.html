What the ACE actually holds

Orca decides “slot 2 holds the magenta”. Nothing checks the machine agrees. A plan that contradicts the loaded spools prints the wrong colours at full speed and says nothing — the highest-consequence gap left in the feature.

The comparison is not two-valued. AceSlot::identity_trusted() already distinguishes a spool the ACE read from RFID or that you set by hand from one it merely inferred. A design that shouts “wrong filament” when the machine simply does not know would train people to ignore it. So: agrees, disagrees, cannot tell.

State B is drawn from what this printer actually reported while the feature was being built — PETG Kingroon #83AFFF named by hand in S1, the rest empty. S4 is shown holding an unidentified spool so the third verdict is visible; the machine's real S4 was empty.

State AThe machine agrees
Situation
Every ACE slot the plan uses holds the spool it expects.
Behaviour
One quiet line. Nothing to decide, so nothing is asked.

The cheap case, and the common one. It has to stay this quiet or the loud case stops meaning anything.

State BThe machine disagrees
Situation
The plan wants four PLA spools. The ACE reports PETG in S1, nothing in S2 and S3, and something in S4 it has not identified.
Must claim
Which slots are wrong, which are merely unverified, and what each choice costs.
At stake
Whether this blocks the print, and whether Orca offers to bend the plan to the machine.

Two ways out, and they are not symmetric. Use what is loaded re-plans around the spools actually present — free, instant, but it cannot invent a magenta that is not in the machine, so it only resolves slots where a match exists elsewhere. Load these spools keeps the plan and turns the panel into a checklist. Orca does not move filament itself: the ACE write commands are documented but have never been exercised from here, so offering a “load it for me” button would be a promise this code cannot keep.

State CNo answer from the machine
Situation
The ACE endpoint is LAN-only. Over a cloud connection, or with the printer off, there is nothing to compare against.
Behaviour
Say the check did not run. Do not imply agreement — and do not block, since there is nothing the user could do about it.

The failure mode to avoid is a green tick that means “could not check”. Silence and agreement must not look the same.

Settled — this is what was built

  1. Inside the assignment dialog, as a strip under the machine map: the plan and its reality in one place. The panels above are drawn standalone for legibility; in the app they are that strip.
  2. Blocking, with an explicit override. While any slot is unresolved, Apply to plate is disabled and a Print anyway — I have checked the spools tick appears. Closing the dialog instead abandons the export or print rather than quietly proceeding.
  3. Colour + material, brand ignored.
  4. Unverified counts as unresolved. The label still says “cannot tell” rather than “wrong”, because the remedy differs — name the spool on the printer, or swap it — but it holds the gate shut either way. Not knowing is not evidence the plate is safe.
  5. “Use what is loaded” was dropped. It rewrote the user's own assignment on their behalf, which is exactly what Manual mode already does deliberately: drag the spools to where the machine has them and the verdicts clear as you go. One tool, not two.

The gate is re-checked in C++ against the layout actually committed, not the one the dialog opened on — so resolving a mismatch by moving spools genuinely resolves it, and closing the dialog cannot skip the check.
