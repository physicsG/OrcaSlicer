More colours than places

A plate can ask for more filaments than the machine has room for: three stock feeders plus a four-slot ACE hold seven, and an eight-colour plate has nowhere to put the eighth. The planner correctly returns infeasible. What happens next is the problem.

This is not a hypothetical. I sliced the seven-colour cube with the ACE set to two slots — five places, seven colours — and read the file it produced.

TodayWhat the slicer actually wrote

Observed, not inferred

  • Slicing succeeded. No error, no warning, no notification.
  • The plan header came out empty — not "infeasible", just blank.
  • The file addresses heads that do not exist: 300 tool changes to T4, T5, T6 on a four-head machine, with matching M109 … T5 and SM_PRINT_PREEXTRUDE_FILAMENT INDEX=5.
  • Not one ACE_SWAP_HEAD. The ACE is never told to do anything.
; multiACE plan: ← empty
M109 S220 T5
T5
SM_PRINT_PREEXTRUDE_FILAMENT INDEX=5

Orca's own contract for this feature is “tool numbers are physical heads only; no T4–T6 leaking through”. When the plan is infeasible the remap is empty and that contract breaks silently. Whether the firmware ignores T5, faults, or does something worse is unverified — and not something to find out by sending it.

The dialog does open, but it misdiagnoses: it says “These pins cannot all be satisfied. Unpin something to get a plan.” There are no pins — C++ sends none when the plan is infeasible. It blames a constraint the user never set for a capacity problem they did. The board also just omits the two filaments that did not fit, and the load plan lists ACE 1 · S0 twice.

ProposedRefuse, and say how short

Three changes. The dialog names the shortfall and lists the filaments with nowhere to go, rather than dropping them off the board. Apply is disabled with no override — unlike a spool mismatch, no amount of user confidence makes a fifth place exist. And because the gcode is written before this dialog is ever opened, slicing itself refuses: the plate does not get a file at all.

What I need from you

  1. Should slicing refuse, or just warn? I recommend refuse — raise it as a slicing error the way an unprintable model does, so no file exists to send. Warning-only leaves a T4–T6 file on disk that looks finished.
  2. Hard block, or an override like the ACE check has? I recommend hard: a wrong spool is a judgement call, a missing toolhead is not.
  3. What should it suggest? Drawn with all three routes — remove filaments, give a head more slots, or merge two colours. Naming the least-used colours as removal candidates is possible: slicing knows how much each one is used.
  4. Show the unplaced filaments in a tray as drawn, or leave the board to the ones that fit and name them only in the message?

Where it goes

Slicing: Print::process already knows — it holds the infeasible LoadingPlan at the end of psWipeTower, which is the moment to throw a SlicingError naming the shortfall. Dialog: the page's infeasible branch needs to stop blaming pins, and C++ needs to send the capacity and the used-filament count so the message can be specific. Gate: the same AceReview::Abort path the ACE check already uses.
